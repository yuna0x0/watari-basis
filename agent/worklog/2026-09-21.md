# 2026-09-21

## A report from a VRCFury avatar with its toggles in prefabs of their own

A user converted an avatar built from 57 prefabs: the body, clothing prefabs, and one small
prefab per menu toggle, each holding a VRCFury Toggle and nothing else. The report and four
screenshots of the written controls showed three faults.

**Toggle actions were resolved against the toggle's prefab.** `VrcFuryToggleResolver` searched
`source.Root` for an `allRenderers` blendshape action and an `affectAllMeshes` material action.
A toggle prefab holds no renderer, so 44 actions were reported `vrcfury.action.unresolved`, 27
controls dropped as `vixxy.nothingToSwitch`, and 6 of 33 toggles were rebuilt. VRCFury's
`BlendshapeActionBuilder` iterates `avatarObject.GetComponentsInSelfAndChildren` and its
`MaterialPropertyActionBuilder` calls `FindRenderers(affectAllMeshes, renderer, avatarObject)`,
read from the repository. Decision 0018: every Vixxy target is a transform of the scanned
hierarchy. `HierarchyLocator` maps a source asset's transform to the hierarchy through the
source's placement path; `plan.HierarchyRoot` names the scanned object; `TryTranslate` with no
source translates from it. Modular Avatar and expression-menu toggles go the same way. Full
Controllers keep prefab-relative paths and use the prefab's live instance as their path root,
or the avatar when the bindings apply to it.

**Rest values came from the asset.** The three clothing controls in the screenshots had every
blendshape and discard property at 0 on both OFF and ON, so all three did the same thing:
switch one object on. ON = 0 is what the toggles set (un-hide the part). OFF was filled from the
prefab asset's renderer and material, while the hidden rest state lives in overrides on the
instance. Resolving subjects in hierarchy space makes `FillBlendShapeDefaults` and
`FillMaterialDefaults` read the instance. Test: an instance blendshape override becomes the
OFF choice.

**Eight items skipped at write time were never named.** `ConversionReport.Group` took the plan
only, so the converter's `apply.unresolved` lines reached neither the file nor the window, and
`TotalSkipped` counted rigs and constraints only. The report now groups the result's diagnostics
too, counts Vixxy, head chop, link and descriptor skips, and lists every distinct message under
a warning. The probable cause of those eight: armature links moved the clothing bones before
the rigs and constraints on them were located by sibling-index path. `AvatarConverter.Apply`
now locates everything, then links, then writes. Test: a PhysBone on the clothing fixture's
Frill bone is written after the link. Unverified on the reported avatar.

Smaller: `vixxy.rebuilt` and its siblings were emitted per toggle call ("(8): 1 menu toggles");
`constraint.source.overflow` fired for an empty slot because empties were dropped before the
compare; script id `67cc4cb7…:1610797297` is `VRCSpatialAudioSource`, derived with the MD4
rule and checked against the descriptor's id, now recognised and reported. The report's
`descriptor.animationLayers` line read "(Base, Base)", which no valid descriptor produces. A
test feeding five base layers plus variant overrides through `PrefabOverrides.SetPath` and the
reader is added to find out whether the override path is at fault.

The reported avatar is not available here. Fixtures: `SampleVrcFuryToggleOnly.prefab`, a toggle
with a blendshape action and no renderer, nested under the VRCFury sample; a PhysBone on the
clothing fixture's Frill bone.

**Overrides on managed references were never applied.** A toggle prefab's action cannot name
an object outside its own file; the outer prefab sets it as an override on the nested
instance, which Unity records as `managedReferences[<rid>].obj`. `PrefabOverrides.SetPath`
knew `Array.data[i]` only and returned false, so the action kept `{fileID: 0}` and was dropped
without a word, as VRCFury does for an unset action. No local file held an example of that
path, so a probe test builds a prefab with a `[SerializeReference]` field, overrides it on an
instance and reads the path back from `PrefabUtility.GetPropertyModifications`, checking the
id against the saved file's `rid`. `SetPath` now follows the id into `references.RefIds` and
sets the field under its `data` block. Fixture: `SampleVrcFuryNested.prefab` nests the
toggle-only prefab and points its object action at the outer prefab's object.

Suite 350 green before that change, 353 after, no `error CS` in the editor log. The probe
could not use a MonoBehaviour of the test assembly, which Unity refuses to attach as an editor
script; it uses `HVRVixxyControl`, whose property list is serialized by reference. Unity
recorded the override as `managedReferences[<id>].propertyName` with the id equal to the
saved file's `rid`. The layer test passed: the override path
keeps entry types, so "(Base, Base)" is still unexplained and needs the descriptor block from a
file that produces it.

## The user's summary of the 0.11.1 run

Unreleased, after 0.12.0. The user summarised the earlier run: every jiggle rig was rooted on
the PhysBone's own object instead of the bone it named, and those PhysBones sit in a prefab of
their own. Armature links and everything else came through. Their toggles from Full Controllers
were skipped; those resolve into blend trees, which decision 0017 keeps out.

The avatar is not here, so the root fault was traced through the code, where three gaps sat
on that path:

- **A root bone in another prefab was skipped at write time.** The split fixture's PhysBone
  names the outer prefab's Hips, and the plan resolved it, but `TryTranslate` walked a
  sibling-index path from the nested prefab and found nothing. The split tests checked the plan
  only. `TryTranslate` now locates a transform outside its item's prefab through
  `HierarchyLocator` and translates it from the hierarchy root. Test: applying the split avatar
  writes the rig onto the instance's Hips.
- **A variant's base file had no resolver registered.** `CreateForInherited` built one and
  `ResolversByGuid` never saw it, so an override recorded in the base, naming the base's own
  object, could not be answered: `ResolveForeign` found no resolver for the base's guid. Now
  registered. Fixture: a variant of the split avatar, hand-written as a PrefabInstance with two
  stubs; test: the nested PhysBone's root resolves to Hips and the rig is written. The same
  fixture showed the collider index keyed by the source's guid while an override in the base
  names the base's guid, so a collider defined in the base was `physics.collider.unresolved`;
  the index is keyed by the defining file now. The user's report had 26 of those.
- **A chain of one bone was silent.** A root that fell back to the host with nothing below it
  wrote a rig that moves nothing. `physbone.noChain` names it.

Whether the user's roots fell back for one of these reasons is not established; the 0.12.0
report, where the rig lines carry the root names and `apply.*` names skips, will say. VRCFury's
`ArmatureLinkService` was read for its PhysBone rule: a prop bone that is a link root or matches
a humanoid bone is always reparented; children of a PhysBone root and PhysBone chain bones are
not, nor anything under them. `ArmatureLinkPlanner` matches that, so nothing changed there.
