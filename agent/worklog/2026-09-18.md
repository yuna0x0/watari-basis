# 2026-09-18

## Synced the clone to current Basis

Seven upstream commits. One reaches Watari: `BasisAvatar` gained `EyeMaxLookAngleEnabled` and
`EyeMaxLookAngle`, clamped to 1 to 45 degrees with 25 the default, and the local eye driver, the
preview driver, the remote face driver and HVR's eye tracking actuation all read it. The eye
driver's fixed `maxAngleDeg` field is gone. The eye calibration now measures from the avatar's
T-pose facing rather than the head transform, which Watari does not touch. Nothing else moved in
what Watari reads or writes: jiggle physics, constraints, head chop, Vixxy's serialized shape and
the rig's bone requirements are as before. The leg solver changes are numeric tuning. Suite green
before any change; versions row raised.

## Eye rotation limits written to the Basis Avatar

`vrm.lookAt.range` said Basis had no per-avatar limit; that is no longer true, so the diagnostic
and both docs pages were wrong against the synced Basis. The 2026-09-06 entry named this field
as the awaited upstream fix.

Both sources now write the limit. `EyeLookAngleMapper` takes a smallest and largest limit and
plans one angle: the largest, clamped to Basis's range. It reports Mapped when the directions
agree within a degree, `.uneven` when they do not, `.clamped` when the value fell outside 1 to
45, and `.none` when the largest is zero, where 1 degree is written. The writer enables the flag
and sets the angle only when the plan carries one, so a value set by hand on the component
survives a repeated conversion from a source that states none.

VRM: both readers keep all four range map scales instead of the running maximum, so the spread
is known. VRChat: the reader now reads the five gaze states under `customEyeLookSettings`, each a
`linked` flag and a local rotation per eye bone. Read from the SDK's own editor,
`VRCAvatarDescriptorEditor3EyeLook.cs`: `RecordEyeRotations` writes `transform.localRotation`
straight into the state, so a limit is `Quaternion.Angle` between a direction and the straight
state, not identity. A survey of 36 descriptors in the reference project showed why that matters:
one avatar's straight state is a half turn, values run from 1 to 30 degrees, directions differ
on most of them, and two set nothing at all.

## Exponent components were dropped by the value parser

The half-turn test failed with 45 degrees: Unity writes that straight state with a `w` of
`-4.371139e-08`, and the component pattern in `UnityYamlValues` accepted `e` and `+` but not the
minus in the exponent, so `w` was skipped and the quaternion kept its default of 1. Real prefabs
write rest rotations this way (`-4.038968e-28` in the reference project), and the same pattern
serves every Vector3 read: view position, constraint offsets, VRM eye offsets. The pattern now
takes a signed exponent. Found by a test, so recorded here as the kind of fault the fixture data
had never exercised: every fixture value was hand-written without exponents.

## OSC and render pipelines, researched

`agent/research/osc-and-shader-pipelines.md`. Short form: Basis has OSC already, in the HVR
comms package, routing `/avatar/parameters/<name>` to the Vixxy control with address `<name>`,
floats only, and only on an avatar carrying Automatic Face Tracking or OSC Acquisition. Watari
writes controls with no address, so nothing external can reach them by parameter name; that is
the "stable Vixxy address" backlog item. lilToon, SCSS and MToon10 handle URP by themselves.
Poiyomi 10.0.20 ships URP as a separate shader set and package, switched per material by hand;
a bulk remap would be that switch over every material. Materials counted: the user's content is all lilToon, the
reference project has 83 Poiyomi materials, every one locked. The docs now say what each shader
needs and what OSC can and cannot reach. Whether Watari remaps Poiyomi materials is undecided.

## Model instances

A scene object whose prefab source is a model file (FBX, OBJ, glTF) has no prefab file holding
components: a model carries the mesh and the skeleton and nothing else, so everything added on
the instance exists only in the scene. `SceneOnlyComponents` now tells a model instance apart
from a prefab instance through the root's corresponding source object and reports
`source.modelInstance`. A variant saved from a model is a prefab and keeps the old path. Test on
a one-triangle `.obj` fixture with an unpacked sample avatar beneath it. Unreleased.

## The saved scene file as a source

`ScanScene` runs before any prefab is read: it scans the
scene the hierarchy sits in, keeps the documents that belong to it (a MonoBehaviour whose owner
resolves under the root, a PrefabInstance whose id a live object under the root carries), and
adds the scene's PrefabInstance modifications to the plan so instance values land on the prefab
documents first. `PrefabObjectResolver.CreateForScene` indexes live objects through
`GlobalObjectId`: a plain scene object by its target object id, an instance object by its
corresponding source and the target prefab id, which is what a scene stub's
`m_CorrespondingSourceObject` and `m_PrefabInstance` name. The scene's own documents are read
last, after every prefab, and each component stub is registered under the file and id it stands
for, so a scene PhysBone naming a prefab collider finds it in the index. The scene is a
`ConversionSource` with `IsScene`, rooted at the scene object, so nothing it yields is
translated. Unsaved, dirty and binary scenes are reported; the old warnings stay for the case
where the scene could not be read and now say to save it.

Tested on a scene file written from the sample prefab's documents and opened (same counts as
the prefab) and on a model instance with a PhysBone written into the saved scene by hand as an
added component with stubs. The first test began as instantiate, unpack, save: the saved scene
held every missing-script component as `m_Script: {fileID: 0}` with no fields. Unity keeps a
missing script's data only while the object comes from a file; instantiating and unpacking in
memory drops it. So a prefab unpacked in the Basis project cannot be read back by saving, and
the message and docs say so; a scene saved where the scripts existed keeps everything. The readability tests now spawn into an unsaved additive scene, since the
open scene is a source.

Checked on real content: a scene from the reference project whose avatar is an FBX instance
with 49 PhysBones, 38 colliders and the descriptor added in the scene, copied with its FBX into
the Basis project's excluded scratch folder and run headless. All 89 components read from the
scene file, 48 rigs planned (one PhysBone disabled), every root bone a live object under the
instance, and the converter wrote 48 jiggle components. The scratch copy was deleted afterwards.

Not read: a collider added in the scene and assigned to a PhysBone inside a prefab. The prefab
is read before the scene, so the index does not hold the collider yet. Documented.

## Vixxy address from the parameter name

`VixxyWriter` writes the plan's parameter name into `address.path`, skipping the `@System/`
prefix Basis reserves. Basis strips `/avatar/parameters/` from an OSC address and matches the
rest, so a float sent the VRChat way drives the control. Bool and int arguments are dropped by
Basis, which is the limit worth reporting upstream. Reported as `vixxy.address`.

## Nothing is read twice

Two tests answer whether the scene source can double a toggle: a VRCFury prefab instance in a
saved scene plans the same components, toggles, links and controls as the prefab alone, and
the same components living only in a scene file plan the same controls once. A prefab's
components appear in the scene file as stubs, which every reader skips. The report now names
parameters that drive more than one control, `vixxy.sharedParameter`, so a real duplicate
shows by name; two layers on one parameter, the known shape, show there as well.
